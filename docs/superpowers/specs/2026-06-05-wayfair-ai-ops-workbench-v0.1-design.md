# Wayfair AI 运营工作台 v0.1 需求说明

日期：2026-06-05

## 1. 阶段判断

当前项目不再处于“洞察需求”阶段，而是进入“打磨需求”阶段。

已确认的真实需求不是“做一份月报”，也不是“把 Wayfair 报表做得更好看”，而是：

> 将 Wayfair 后台、广告、Cost Stack、YB 成本、订单、库存、Listing Health、客诉扣款等分散数据，转成可执行的 SKU 运营动作。

项目当前已经具备 MVP 雏形：

- 已有 Dashboard 外壳和报告导航。
- 已有 SKU 分级、促销准入、定价体检、库存映射、广告调整、数据补齐清单。
- 已经接入真实 5 月和 6 月初数据。
- 已经形成 Cost Stack、订单毛利、广告、促销和 Listing 的基本判断口径。

下一步重点不是继续堆报告，而是把这些报告收敛成一个可执行的运营工作台。

## 2. 目标用户

v0.1 只服务一个用户角色：

**Wayfair 店铺经营者 / 运营负责人。**

当前实际用户是店铺老板本人。用户主要负责：

- 提供 Wayfair / YB / 库存 / 广告等原始数据。
- 按系统给出的动作去后台执行。
- 对少数需要人工判断的数据进行确认。

系统负责：

- 整合数据。
- 识别问题。
- 给出优先级。
- 生成可执行任务。
- 保留复盘依据。

## 3. 核心痛点

### 3.1 数据很多，但动作不清楚

Wayfair 后台能导出大量报表，但用户真正需要的是：

- 今天先处理哪些 SKU？
- 哪些 SKU 不能促销？
- 哪些 SKU 可以保守投广告？
- 哪些 SKU 要先查库存？
- 哪些 SKU 要修 Listing？
- 哪些 SKU 要复核成本或 Base Cost？

### 3.2 口径容易误判

典型风险：

- 用 `Wholesale Cost - Total Cost` 误判平台亏损。
- 只看广告 ROAS，不看真实利润和库存。
- 只看订单毛利，不扣广告、客诉、退货和其他开支。
- 只看前台价，不看 Base Cost、Cost Stack 和平台空间。

### 3.3 报告有了，但没有形成执行闭环

当前报告已经能说明很多问题，但用户每天打开系统时，仍需要在多个页面之间判断：

- 哪些最急？
- 哪些今天做？
- 哪些等数据？
- 哪些已经做过？
- 做完后效果如何？

v0.1 要把“分析报告”推进成“执行清单”。

## 4. v0.1 产品定位

产品名称：

**Wayfair AI 运营工作台 v0.1**

一句话定位：

> 打开后 10 分钟内，告诉 Wayfair 店铺经营者今天最该处理的 SKU、原因和具体动作。

v0.1 不追求自动化所有后台操作，只追求把数据判断转成清晰执行。

## 5. MVP 成功标准

v0.1 成功，不以页面数量衡量，而以执行效率和运营结果衡量。

### 5.1 使用成功

用户打开系统后，10 分钟内能回答：

- 今天优先处理哪 10 个 SKU / Listing？
- 每个 SKU 为什么被排进来？
- 要执行什么动作？
- 执行前还缺什么数据？
- 哪些 SKU 今天不要动？

### 5.2 业务成功

连续 4 周使用后，需要能复盘：

- 广告浪费是否下降。
- 禁促 SKU 是否避免进入深折扣。
- Listing 修复后是否提升点击或转化。
- 定价风险 SKU 是否减少。
- 缺库存或库存映射不准导致的误投是否减少。

### 5.3 系统成功

系统每周至少稳定输出：

- 一份优先级执行清单。
- 一份待补数据清单。
- 一份已执行 / 待执行 / 暂缓的任务状态。

## 6. v0.1 只解决什么

v0.1 只解决一个主问题：

> 从所有数据里提炼出“本周必须处理的 SKU 任务清单”。

清单必须包含：

| 字段 | 说明 |
|---|---|
| 优先级 | P0 / P1 / P2 |
| SKU / Listing | 明确到执行对象 |
| 问题类型 | 广告、促销、定价、库存、Listing、客诉、数据缺口 |
| 触发原因 | 为什么被系统抓出来 |
| 建议动作 | 用户具体去做什么 |
| 执行前检查 | 需要先确认的数据 |
| 当前状态 | 待执行、执行中、已执行、暂缓、等数据 |
| 复盘指标 | 下次看什么结果 |

## 7. v0.1 不解决什么

为了避免产品范围失控，v0.1 明确不做：

- 不做多店铺 SaaS。
- 不做用户注册、权限、计费。
- 不做自动登录 Wayfair。
- 不做自动改价。
- 不做自动调广告预算。
- 不做自动创建促销。
- 不做完整财务系统。
- 不做复杂 BI 图表系统。

这些都可以以后做，但不能进入 v0.1。

## 8. 方案比较

### 方案 A：继续做更多报告

优点：

- 实现快。
- 不破坏现有结构。
- 每个报告能解释一个具体问题。

缺点：

- 页面越多，用户越不知道先看哪个。
- 仍然需要人脑把报告转成动作。
- 不容易验证系统是否真的提升运营效率。

### 方案 B：做“执行中心”

优点：

- 最贴合用户真实需求。
- 能把现有报告沉淀成行动。
- 方便按周复盘执行结果。
- 是后续商业化的核心雏形。

缺点：

- 需要定义统一任务字段。
- 需要从多个报告抽取同一套 SKU 动作。
- 初期可能还要人工确认部分任务。

### 方案 C：直接做自动化后台操作

优点：

- 想象空间大。
- 如果成功，可以极大减少人工操作。

缺点：

- 风险高。
- Wayfair 后台权限、规则和误操作成本都高。
- 当前判断模型还没经过足够运营验证，不适合直接自动执行。

推荐方案：

**先做方案 B：执行中心。**

理由：

当前项目已经有足够多分析报告，缺的是把报告统一成每日/每周动作。先做执行中心，可以最快验证这个产品是否真的能帮店铺运营，而不是继续停留在“报告好看”。

## 9. v0.1 信息架构

### 9.1 首页：今日 / 本周执行中心

首页不再只是报告入口，而要优先展示：

1. 本周必须执行
2. 等数据
3. 禁止操作
4. 已完成待复盘
5. 快速进入 SKU 详情

首页的第一屏应该回答：

> 今天我先做什么？

### 9.2 SKU 任务清单

这是 v0.1 的核心页面。

任务来源包括：

- SKU 分级
- 促销准入
- 定价体检
- 库存映射
- 广告调整清单
- Listing Health
- Customer Feedback
- Cost Stack
- YB 订单利润和客诉扣款

任务按优先级排序：

- P0：有明确亏损、误投、禁促、定价风险或库存风险，必须先处理。
- P1：有转化/广告/Listing 机会，处理后可能提升销售。
- P2：观察型、新品型或等数据型任务。

### 9.3 SKU 详情页

每个 SKU 应该有一页完整档案。

必须展示：

- SKU / Listing / 产品名
- SKU 分级
- 当前状态
- 库存映射和库存风险
- 订单表现
- 广告表现
- 定价体检
- Cost Stack 明细
- 促销准入
- Listing Health
- 评分评论
- 客诉扣款
- 系统建议
- 人工备注

SKU 详情页目标不是展示更多表格，而是支撑一个判断：

> 这个 SKU 接下来应该放量、保守观察、先修复，还是暂缓/禁促？

### 9.4 数据补齐中心

保留现有数据补齐清单，但要升级成任务来源。

每条数据缺口要说明：

- 缺什么
- 去哪里下载
- 用来判断什么
- 如果没有这份数据，会影响哪些结论

## 10. 任务生成规则 v0.1

### 10.1 广告任务

触发条件示例：

- 有花费但无订单。
- 有点击但 CVR 低。
- 有订单但真实毛利低。
- SKU 库存不足或库存映射不可靠。

动作示例：

- 暂停或降到最低预算。
- 保留小预算观察。
- 先修 Listing 再投。
- 先查库存再加预算。

### 10.2 促销任务

触发条件示例：

- 订单毛利率低于 20%。
- 平台空间偏低。
- 大促 2B 利润率低于 12%。
- 客诉/退货异常。
- 库存不足。

动作示例：

- 禁止深折扣。
- 只允许 5% 轻促。
- 等 Listing 修复后再促销。
- 先复核成本或 Cost Stack。

### 10.3 定价任务

触发条件示例：

- Base / 前台价高于 72%。
- 平台空间低于 16%。
- 供货价竞争百分位偏高。
- 当前 Base 下真实毛利不足。
- 缺成本或缺前台价。

动作示例：

- 不要先提 Base。
- 先降拿货、包装或发货成本。
- 补成本后再判断。
- 等有效 6 月 Cost Stack 后复核。

### 10.4 Listing 修复任务

触发条件示例：

- Required Tag Coverage 低。
- 图片不足。
- Review 少。
- 有点击但不转化。
- Customer Feedback 出现 Damage、Missing Parts、Defect 等问题。

动作示例：

- 补 TAG。
- 补图片。
- 修说明书 / 包装 / 配件。
- 优先处理有广告花费或历史订单的 SKU。

## 11. 数据流

v0.1 数据流：

1. 用户提供 Wayfair / YB / 库存等原始数据。
2. 脚本生成脱敏 SKU 汇总。
3. 各专项报告输出判断。
4. 执行中心汇总专项判断。
5. 系统生成任务清单。
6. 用户按任务执行。
7. 下周或下月导入新数据复盘。

核心原则：

- 原始敏感数据不进入线上页面。
- 线上只展示脱敏 SKU 级汇总。
- 所有动作都要保留触发依据。
- 不能只给结论，不给原因。

## 12. 错误处理和护栏

系统必须保留以下护栏：

- 6 月 Cost Stack 如果是 0 行，不能用于价格结论。
- 库存映射低置信，不能直接用于广告/促销判断。
- 缺成本的 SKU 不能做提价/促销结论。
- 缺前台价的 SKU 不能做 Base / 前台价比例判断。
- 有客诉扣款的 SKU 不能直接放量或进深折扣。
- 订单毛利没有扣广告、固定开支、仓储、人工、汇损时，不能当作最终净利润。

## 13. 第一版页面清单

v0.1 应新增或改造 3 个页面：

1. **运营执行中心**
   - 本周必须执行
   - 等数据
   - 禁止操作
   - 已完成待复盘

2. **SKU 任务清单**
   - 所有任务按优先级聚合
   - 可按问题类型筛选
   - 可按状态筛选

3. **SKU 详情页**
   - 每个 SKU 的完整经营档案
   - 支持从任务清单点击进入

现有报告继续保留，作为证据层，不再作为用户的第一入口。

## 14. 验证计划

v0.1 先用当前店铺验证，不对外推广。

验证周期：

**4 周。**

每周记录：

- 系统生成了多少任务。
- 用户实际执行了多少。
- 哪些任务判断正确。
- 哪些任务判断错误。
- 哪些任务因为缺数据无法执行。
- 广告浪费是否下降。
- Listing 修复后是否有转化改善。
- 禁促和定价护栏是否避免误操作。

如果 4 周后能证明：

- 用户每天打开系统后知道先做什么；
- 至少 70% 的 P0 / P1 任务被执行；
- 任务能减少错误投放、错误促销或错误定价；

则 v0.1 验证成功。

## 15. 下一步

本需求说明确认后，进入实现计划阶段。

实现计划应包含：

1. 设计统一任务数据结构。
2. 从现有 CSV / HTML 报告中生成任务清单。
3. 新建运营执行中心页面。
4. 新建 SKU 任务清单页面。
5. 设计 SKU 详情页数据结构。
6. 将首页入口从“报告集合”调整为“执行中心优先”。
7. 做本地和线上页面验证。

## 16. 自检结论

本需求说明没有把范围扩大到 SaaS、自动化改价或自动化广告操作。v0.1 聚焦在一个明确目标：

> 让用户打开系统后，快速知道本周最应该处理哪些 SKU，以及为什么、怎么处理。

该范围可以在现有项目结构上落地，不需要重构整个系统。
